Paradigm

Manual vs Automated

Bukan musuh — mitra dengan peran berbeda

Manual Testing

  • ✓ Exploratory — temukan bug tak terduga
  • ✓ UX judgment & visual inspection
  • ✓ Cocok untuk fitur baru & prototype
  • ✗ Lambat untuk regression berulang
  • ✗ Human error, tidak konsisten
  • ✗ Sulit scale ke ratusan test case

Automated Testing

  • ✓ Regression guard — cegah bug terulang
  • ✓ Konsisten, cepat, bisa dijalankan kapan saja
  • ✓ Scale ke ratusan test case + CI
  • ✗ Setup awal butuh effort
  • ✗ Maintenance saat UI berubah
  • ✗ Tidak replace exploratory testing
Best practice: Manual untuk discovery · Automated untuk regression & confidence

The solution

Playwright QA Kit

Operating model: Validate → Plan → Generate → Execute → Heal → Report

0. Validate→ 1. Plan→ 2. Generate→ 3. Execute→ 4. Heal→ 5. Report

Komponen utama

  • •requirements/ — template + skenario terstruktur
  • •MCP servers — playwright · playwright-test · playwright-qa
  • •Agent files — Planner, Generator, Healer, Reporter
  • •Hermes Agent — orchestrator via .mcp.json
  • •Custom dashboard — Table + Accordion + export

Entry point utama

  • •npm run qa:run — preflight + prompt + dashboard
  • •npm run validate:requirement — cek 1 file req
  • •list_requirement_status (MCP) — coverage map
  • •Auth multi-role: .auth/{APP_ENV}/role.json
  • •Exit: APPROVE / FILE BUG / REVISE REQ / FIX TEST / FIX ENV / BLOCKED
MCP
Model Context Protocol — 3 servers: playwright (browser), playwright-test (run), playwright-qa (validate/report/snapshot).
Hermes
AI agent — membaca AGENTS.md + .mcp.json, menjalankan pipeline 6 fase untukmu.
qa:run
CLI entry point: preflight + cetak prompt Hermes dinamis per requirement + buka dashboard (default ON, skip: --no-open-dashboard).
Agent
Peran AI per fase (Planner/Generator/Healer/Reporter) dengan instruksi & tools berbeda — di .github/agents/.

Buka /login 2. Isi email & password valid 3. Klik Login **Hasil yang Diharapkan:** - Toast "Berhasil Login" - Redirect /dashboard

2. Prompt ke Hermes

Jalankan pipeline QA untuk requirements/login.md

Agent otomatis

  • ✓ health_check
  • ✓ validate_requirement
  • ✓ parse scenarios + roles
  • ✓ tulis specs/login-test-plan.md
  • ✓ Coverage Gap section
Requirement
Dokumen kontrak uji (bukan prompt bebas): metadata + skenario + hasil yang diharapkan — bisa divalidasi machine-readable.
SC / TC
SC = skenario di requirement. TC = Test Case ID di spec/report (mis. TC-LOGIN-001) untuk traceability.
Auth state
Status login saat test mulai: unauthenticated (belum login) atau pakai session tersimpan di .auth/.
Coverage Gap
Bagian di plan yang jujur soal apa yang tidak ditest — biar ekspektasi stakeholder realistis.

Workflow 3/3

Heal & Report

Perbaiki flaky, putuskan exit criteria

5. Healer

  • • get_test_failures + trace/screenshot
  • • Klasifikasi 6 failureSource
  • • Seed pattern (network, hybrid, auth)
  • • Fix locator / assert / serial mode
  • • Re-run targeted specs

6. Reporter + QA Decision

  • • Dashboard: Table + Accordion view
  • • SOURCE column + Evidence card
  • • Export Confluence / CSV / TSV
  • • archive_report(runId) opt-in

APPROVE

Semua pass → baseline

FILE BUG

failureSource: app

REVISE REQ

requirement ambigu

FIX TEST

locator / AI gen

FIX ENV

auth / seed / URL

BLOCKED

blocker didokumen

failureSource
6 sumber: app (bug produk), test, env, requirement, ai_generation, unknown. Dashboard kolom SOURCE menampilkan Cause + Do + blurb.
Evidence card
Dashboard section collapsed default: N retried · N trace · N screenshots · N video + deep links ke Playwright HTML.
Flaky
Test kadang pass/kadang fail — timing, parallel, atau data shared. Healer klasifikasi & fix.
Baseline
Run yang di-approve & diarsip via npm run archive:save — rujukan hijau untuk regresi.

Scenario tags

@success @failure @access-restriction @network @hybrid @aria @visual @manual @download @upload @file-content @network-assert

Assert PDF/Excel teks (bukan layout). Pakai assertPdfContains, readExcelSummary.

@upload

Showcase 3/4

Role-Aware & Auth

Satu framework untuk single-user maupun multi-role

Mode 1 — Single user

TEST_USER_EMAIL=... TEST_USER_PASSWORD=... → .auth/user.json

Mode 2 — Multi-role

FINANCE_EMAIL=... HRD_EMAIL=... → .auth/finance.json → .auth/hrd.json

Konvensi file: src/tests/<feature>-<role>.spec.ts + test.use({ storageState: '.auth/finance.json' })

Day-2 ganti password: npm run env:edit (decrypt → edit → encrypt, dotenvx-safe)

storageState
File session browser (cookies/localStorage) hasil login sekali — test berikutnya skip form login.
.auth/
Folder session per role (gitignored). Diisi auth setup, dipakai project Playwright.
dotenvx
Enkripsi nilai di file .env — kredensial tidak tersimpan plain text di disk/repo.
env:edit
CLI day-2: decrypt aman → edit role/password → encrypt ulang + verifikasi decrypt.
